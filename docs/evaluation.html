찾고, 읽고, 재사용하고, 일을 끝낸다.

설치 여부만으로 LLM 결과 품질이 달라지지는 않는다. 같은 지침·파일·도구·버전이 실제로 사용된다면 본질적인 차이는 없다. 차이는 최초 획득 비용, 호출 성공률, 컨텍스트, 의존성 준비와 재사용 방식에서 발생한다. 이번 구현은 반복 사용 비용과 실패 처리의 개선을 검증했다. 결과물 품질의 보편적 우위는 아직 검증하지 않았다.

1. 경쟁 제품에서 우리가 놓친 것

vercel-labs/skills, commit 92a9a34와 npm 배포물 skills@1.7.4를 확인했다. find-skills는 사용자의 도메인·작업을 파악하고 설치 수·평판·GitHub 스타를 확인하도록 이미 지시한다. 또한 CLI에는 skills use가 있으며, 영구 설치 없이 파일을 준비하고 기본적으로 프롬프트를 stdout에 출력한다. --agent로 별도 에이전트를 시작하는 것은 선택사항이다.

따라서 “설치하지 않는다”, “현재 대화에서 쓴다”, “인기 지표를 본다” 자체는 차별성이 아니다. upstream은 일부 소스에 미리 만들어진 다운로드 스냅샷을 사용하고 여러 에이전트·프로바이더·비공개 소스를 지원한다. 이번 구현도 이 스냅샷 API를 활용하도록 개선하되, 선택한 커밋의 파일 해시와 일치하는 내용만 채택한다. 이를 단순 git clone 도구로 묘사하거나 콜드 다운로드가 반드시 느리다고 주장하지 않았다.

2. REA 분석 근거

요청대로 GitHub 소스 읽기와 별개로, 실제 npm 배포 디렉터리를 REA analyze_javascript_application으로 정적 분석했다. 분석 대상은 bin/cli.mjs와 dist/cli.mjs. 54,525 AST 노드, 파싱 실패 0. 13개 나머지 파일은 분석 범위 밖이며 의미 그래프는 10,000 노드 한도로 일부 생략됐다. 정적 분석을 런타임 실행 증명으로 취급하지 않았다.

REA가 찾은 dist/cli.mjs의 fetch 후보(6057행)와 검색 함수(6049행), 임시 파일 준비 함수(8294행), prompt 출력 함수(8285행)를 배포 코드 및 동일 버전 소스와 교차 확인했다. telemetry/audit 경로도 별도로 식별하고 비교 실행에서는 모두 비활성화했다. 배포 가능한 근거 요약과 전체 로컬 증거 번들은 연구용 디렉터리에 보존하고 배포 소스에서는 제외한다. 정적 분석과 이후 실행 측정의 근거를 혼동하지 않는다.

3. 속도: 확인된 차이

전체 새 Node 프로세스의 실행 시간을 측정했다. 양쪽 모두 패키지는 이미 준비된 상태이며 npx 최초 설치 비용을 포함하지 않았다. 실행 순서를 번갈아 배치하고 시작 워밍업 3회를 제외했다. 검색 재현에서는 동일한 후보 5개와 동일한 40ms 서버 지연을 사용했다. 두 도구의 최대 결과 수를 20개로 맞췄다.

4. 선택 기준: 정교해 보이는 점수보다 검증 가능한 조건

후보를 판단하는 근거는 작업(operation), 결과물·스택(artifact/stack), 제약(constraints), 실제 사용 가능한 도구·의존성(dependencies) 네 가지다. 각 항목을 supported / contradicted / unknown으로 구분하고 실제 지침이나 파일에서 근거를 찾는다. 필수 조건에 모순이 있으면 제외하고 중요한 unknown을 해소하지 못하면 사용하지 않는다.

적합 후보 = 필수 조건에 모순이 없고 중요한 unknown이 해소된 후보
선택 = 작업에 직접 맞는 지침 우선 → 동등한 적합성에서는 GitHub stars → installs
필요하지 않거나 적합 후보가 없으면 = 스킬 없이 원래 작업 계속

LLM이 지침의 의미를 해석한다. 이를 학습된 통계 모델이나 교정된 성공 확률로 포장하지 않는다. BM25는 장애 시 이미 읽어둔 지침에서 후보를 찾는 검색 함수다. 현재 스타는 최근 성장률이나 GitHub Trending 순위가 아니다. 이번 버전은 Trending 전체 수집기를 구현했다고 주장하지 않는다. 관련성 판정 모델의 품질은 아래 평가로 검증해야 한다.

5. 캐싱과 변경 수집의 실제 구현

검색·저장소 메타데이터·브랜치는 600초 TTL과 조건부 요청을 사용한다. 선택한 커밋의 tree는 불변으로 캐시하고 파일은 Git blob hash로 저장한다. 다른 파일만 바뀐 새 커밋은 기존 스킬 디렉터리를 재사용한다. 지원 파일 하나가 바뀌면 그 파일만 다운로드한다. 캐시에 없는 파일이 4개 이상일 때는 skills.sh 스냅샷을 먼저 시도하고, 각 파일을 고정 커밋의 Git blob hash와 대조한다. 오래되거나 부분적인 스냅샷에서는 일치하는 파일만 재사용하고 나머지는 고정 커밋에서 받는다. 준비된 파일의 상대 경로를 보존하고 재사용 시 바이트 동일성을 검사한다.

refresh --limit 10은 가장 오래 확인한 추적 레코드부터 검사하는 1회 실행 명령이다. 스케줄러에 연결하면 10분 주기로 쓸 수 있지만 이번 작업에서 개인 컴퓨터에 데몬을 등록하지 않았다. 수천 개 저장소를 매번 전수 조회하는 구조가 아니며, 현재는 요청 기반 로컬 카탈로그다. 별·라이선스 메타데이터는 커밋과 별개로 갱신한다. “커밋이 같으므로 스타도 같다”라는 가정을 하지 않는다.

다른 스킬의 코드를 자동 실행하지 않고 검토 후 호스트 도구로 실행한다. hash 검증은 동일성 증명이지 보안 감사가 아니다. 부분 tree, symlink, 변조, 누락된 필수 자원을 성공으로 숨기지 않는다. README는 설명용 증거이며 최고 우선순위 지침이 아니다.

6. 구현 검증과 현실적 한계

21개 테스트 통과: 심볼릭 링크 등록 후 CLI 실행, 디스크 캐시의 프로세스 간 재사용, TTL/304, 빈 결과와 장애 구분, stale 경고, offline miss, 상대 경로 보존, 커밋 고정 오프라인 준비, 스냅샷의 파일별 버전 검증·fallback, 변경 파일만 받기, 변경 없는 refresh, 부분 tree 거부, symlink·hash 불일치·경로 탈출 거부, 이름 불일치, BM25 fallback, 동시 준비, 토큰의 외부 호스트 유출 방지. 공식 skill-creator 형식 검사도 통과했다.

실제 GitHub에서 find-skills와 React best-practices를 내려받아 smoke 검증했다. React 스킬은 76개 파일을 준비했고, 스냅샷 경로가 그중 아직 캐시되지 않은 75개 파일을 한 번에 공급했다. 완전히 빈 로컬 캐시에서 선택 커밋을 지정한 단일 실행은 총 5개 HTTP 요청, 내부 측정 약 788ms였다. 단일 관찰이며 경쟁 제품과의 콜드 다운로드 우위 주장에 사용하지 않는다. 이것은 파일 준비 검증이며 실제 React 작업 결과의 품질 평가가 아니다. 지원 범위는 공개 GitHub, 완전한 tree, 스킬당 200파일/20MiB/파일당 2MiB이다. MCP 도구 설치·키 발급·비공개 소스·외부 디렉터리 의존성까지 자동 해결하지 않는다.

7. 결과 품질 우위를 입증하는 다음 기준

속도 개선을 품질 개선으로 대체하지 않는다. 동일 모델·버전·토큰 예산·프로젝트 상태로 (A) 스킬 없음, (B) find-skills + skills use, (C) hot-pick, (D) 정답 스킬 사전 설치를 비교해야 한다. UI 개선·React 성능·바이너리 분석·문서·스킬 불필요 작업을 포함하고 후보 설명만 바꾼 광고성 케이스도 넣는다.

사전에 결과물 수용 기준을 정한 최소 30개 독립 작업을 출발점으로 삼고 효과 크기에 따라 표본을 늘린다. 평가자는 도구명을 모르게 하고 순서를 무작위화한다. 주 지표는 작업 성공률, 부 지표는 불필요한 질문 수·잘못된 스킬 적용률·완료 시간·모델 토큰·네트워크 요청이다. 쌍별 성공 여부는 exact McNemar, 작업별 시간 차이는 paired bootstrap으로 보고하되 동일 작업 재시도를 독립 표본으로 세지 않는다. ‘필요 없는데도 스킬 적용’은 별도 실패로 기록한다. 아직 이 평가를 실행했다고 주장하지 않는다.

8. 제품 컨셉과 전달 범위

하나의 큐레이터 스킬을 연결하면, 에이전트가 필요할 때 적합한 지침을 찾아 읽고 원래 일을 끝낸다. 사용자는 수백 개 스킬을 관리하지 않는다. 첫 통합은 필요하며 어떤 호스트에서든 모든 프롬프트를 강제 가로채는 제품은 아니다. 당장은 스킬 + 의존성 없는 CLI가 맞다. 공유 대규모 카탈로그와 여러 클라이언트의 도구 호출이 필요해질 때 서버/API 또는 MCP 어댑터를 분리한다.

코드는 새 독립 저장소에 작성했고 기존 Dutying 제품·CI·배포에는 손대지 않았다. 원격 저장소가 없어 push/PR/배포는 하지 않았다. 연구용 다운로드와 캐시는 git에서 제외했다. 초기 설계서의 전체 수집 서비스와 현재 완성된 로컬 스킬을 혼동하지 않도록 이 문서를 구현 기준으로 삼는다.
