Git dates are normalized display metadata

At the repository owner's request on 2026-11-11, Git author and committer dates are assigned to the preceding weekend in Asia/Seoul, with distributed daytime timestamps. They do not establish when work actually occurred.

The preceding weekend means Saturday/Sunday before the Monday of the actual work week. For example, actual work on 2026-11-11 maps to November 7–8, while work on November 7–8 maps to October 31–November 1. Author identities, messages, trees and parent relationships are preserved; commit IDs change. Initial history timestamps are assigned chronologically within two 10:00–21:00 windows with deterministic bounded jitter.

Future local commits

git config --local alias.weekend-commit '!python3 scripts/weekend-git.py commit'
git config --local core.hooksPath .githooks
git weekend-commit -m "fix: describe the actual change"

The local pre-commit hook rejects commits without explicit dates in the preceding weekend. A pre-push hook checks newly pushed author/committer dates and rejects weekday commits produced by other paths such as merges or rebases. The wrapper sets both dates, preserves identity, and keeps newer commits later than their parent when that parent occupies the same display weekend. Direct GitHub edits, other clones without hooks, and bypassing hooks can evade this local rule; provider timestamps are outside its control.

History rewrite and recovery

python3 scripts/weekend-git.py plan previews mapping. The one-time rewrite --apply requires a clean checkout and the exact hot-pick origin, rejects signed commits, saves a local bundle plus old-to-new mapping under ignored .research/history-backup/, and updates local branch refs with compare-and-swap checks. A local marker and the committed history-map file prevent accidental repeated date shifting, including in later clones. Remote history requires an explicit force-with-lease against the previously observed main SHA.

GitHub push times, Actions logs and runs, hosting releases, benchmark execution timestamps and performance measurements remain real and unchanged. Historical benchmark source SHAs refer to the code actually tested, with a local recovery mapping retained. No claim is made that executions or releases occurred on the display dates.
