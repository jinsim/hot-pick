3. 작업에 맞는 GitHub 오픈소스 활용에 집중한다

2026-11-07 목적 정정: 제품의 목적은 지금 하려는 작업에 적합한 트렌디한 GitHub 오픈소스를 찾아 실제로 활용하는 것이다. 디자인·프런트엔드는 데모 사례가 될 수 있지만 제품 범위를 한정하지 않는다. 대상도 스킬뿐 아니라 라이브러리·CLI·프레임워크·에이전트·MCP 등 작업에 적합한 오픈소스 전반이다. 이 문서의 설치 순위와 홍보 제안은 이 목적을 지원하는 참고 자료로 해석한다. 최우선 제품 정의

기존에 설치된 적합한 스킬이 있으면 바로 사용한다. 그때 hot-pick의 외부 검색 횟수는 0이어야 한다. 스킬이 필요 없는 작업에서는 사용하지 않는다. 전체 도구 호출 중 hot-pick 호출 수를 늘리는 것이 목표가 아니다.

4. 더 오래 유지될 경쟁우위

  1. 작업별 검증 사례: 작업 유형·모델·호스트·스킬 커밋·입출력 조건·검증 결과를 연결한다. “프런트엔드”처럼 넓은 태그를 넘어 어떤 요청에서 도움이 됐고 안 됐는지 남긴다. 공개 가능한 재현 예제부터 쌓는다.
  2. 동작하는 조합: 필요한 MCP·스크립트·런타임이 실제 환경에 있는지 확인한다. 이름이 맞지만 실행 불가능한 후보는 건너뛴다. 제작자가 제공하는 호환성 테스트를 받을 수 있게 한다.
  3. 작업을 방해하지 않는 기억: 프로젝트에서 사용자가 선택한 스킬과 검증된 버전을 로컬에 기억한다. 같은 작업의 후속 수정에서 재검색하지 않는다. 사용자가 명시적으로 바꾸거나 제약·환경이 달라졌을 때 재선택한다.

캐시와 랭킹 수집은 쉽게 복제된다. 공개 평가 데이터도 누구나 재사용할 수 있다. 오픈소스에서 경쟁우위는 비밀 데이터 독점보다 재현 가능한 평가를 꾸준히 유지하는 능력, 제작자 기여, 호환성, 신뢰에서 기대한다. 아직 이런 우위가 확보됐다고 주장하지 않는다.

5. 실제 사용을 측정하는 방법

설치 수에서 실제 사용량을 추정해 만들지 않는다. 향후 호스트 연동으로 다음 사건을 구분한다: 후보 선택 → 파일 준비 → 지침 적용 → 검증 결과 → 다른 작업에서 재사용. 파일을 읽었다는 사실은 적용이나 성공 증거가 아니다.

단순 스킬은 모든 실행을 관찰할 수 없으므로, 호스트가 보고한 적용 여부와 테스트 도구가 확인한 결과를 구분한다. 명시적으로 연결된 기록만 집계한다. 결과 기록은 기본 로컬 저장; 원문 프롬프트·코드 업로드 없이, 사용자가 선택한 공개 사례나 동의한 최소 집계만 공유한다. 이번 작업에서는 수집 기능이나 텔레메트리를 활성화하지 않았다.

6. 공개할 때 보여줄 세 가지

  1. 30초 데모: “이 페이지의 AI 느낌을 줄여줘” → 사용자의 스킬 지정 없이 적합한 지침 선택 → 실제 수정 → 같은 화면 크기의 전후 비교. 추가 대화와 실패도 기록하고 과도하게 편집하지 않는다.
  2. 재현 가능한 비교: 동일 모델·프롬프트·초기 저장소, hot-pick가 선택한 스킬 및 고정 커밋, 실행 시간, 결과물, 평가 기준을 함께 공개한다. 베스트 샷 하나를 전체 성능으로 주장하지 않는다.
  3. 제작자에게 돌아가는 가치: 사용한 스킬의 원작자·저장소·라이선스·버전을 명확히 표시한다. 제작자는 자신의 스킬을 발명하지 않은 사용자의 요청에도 연결되는 유통 경로를 얻는다.

10분은 확인 주기이며 모든 항목을 다시 분석하는 주기가 아니다. 인기 메타데이터 스냅샷과 Git 커밋 변경을 분리하고, 내용 해시가 같은 스킬은 재분석하지 않는다. 같은 원본의 중복과 수집 실패를 기록한다. 우선 로컬 카탈로그와 공개 평가 사례에서 시작하고 대규모 서버는 실제 사용 수요가 생긴 뒤 구축한다.
