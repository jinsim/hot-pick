Hot Pick: launch kit

Prepared 2026-11-11. External posts below are drafts, not submitted. No advertising spend, tracking pixel or paid service.

Positioning

Find trending GitHub open source for the task you already have. Read its pinned source, apply what fits, and verify the result.

Start with developers using coding agents who are tired of browsing tool lists. Lead with a concrete result and source attribution. Do not claim to be the fastest, best, zero-overhead, automatically compatible with every MCP, or proven to save tokens.

English announcement

I built hot-pick because keeping up with GitHub tools and agent skills was becoming another job.

It gives a coding agent one workflow: find relevant open source, inspect a pinned version, apply it to your task, and verify the output.

The catalog is collected without LLM calls. Your existing agent handles intent and selection. It supports libraries and CLI tools as well as skills; it does not automatically provision every MCP.

There are reproducible extraction and keyboard-accessibility examples. The honest tradeoff: cold catalog loading can be slow, and we have not established universal speed, token or quality gains.

Try: npx skills add jinsim/hot-pick --skill hot-pick
https://github.com/jinsim/hot-pick

I'd especially like examples where it selects the wrong tool or adds unnecessary work.

60-second demo script

  1. Show the task and original keyboard-button fixture, including failed Tab navigation.
  2. Run the catalog route using examples/quickstart/task.json. Show elapsed time without cutting it out or implying a cold run is warm.
  3. Show the selected project's name, source commit and license. Open the relevant pinned instructions.
  4. Apply the native button, focus and status-region changes.
  5. Run examples/keyboard-button/verify.mjs. Show six browser checks.
  6. Close with the installation command and the limitation: this is application evidence, not a blind comparison against a no-skill agent.

First feedback cycle

Seek ten voluntarily shared real task results across focused UI fixes, data extraction and developer tooling. Record task completion, unsuitable-selection rate, cold/warm overhead, and voluntary reuse. This is a target, not an achieved user count. Compare GitHub stars, repository traffic and Skills installs separately; none proves active use or task success. Use the repository task-result form instead of adding telemetry.

After failures are understood, publish a second example-led update. Retain negative results. External posting and outreach remain pending explicit posting instructions.
