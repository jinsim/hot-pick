Monitoring and evidence of use

Added 2026-11-21. No internal LLM calls, paid runners, new paid service, or always-on personal computer. Firebase remains on its existing free configuration.

Alerts

The monitor runs after collector completion, on hourly best-effort GitHub cron, on voluntary usage issue changes, and manually. It checks public HTTP availability, a nonempty index, actual updated_at age (120 minutes), and latest completed collector result. Failure opens or reopens one assigned issue mentioning jinsim; healthy checks close it with recovery evidence. Repeated failures update the same incident without comment spam. A new incident/reopen generates a GitHub notification subject to the recipient's settings. Device/email delivery cannot be guaranteed from an API success.

GitHub scheduling is not a reliable clock: monitoring on the same platform may also be delayed or dropped. The 120-minute threshold is evaluated when a check runs, not a promise to notify within 120 minutes. A provider-wide scheduling outage requires an independent external monitor. Alert drill runs are clearly marked and excluded from the real dashboard.

Usage and usefulness

There is no silent telemetry. Users voluntarily generate a local preview, review the exact public fields, then submit a GitHub issue. The CLI sends no network request and includes no task prompt, local path, command, output, credential, or artifact. GitHub identity and the submitted packet are public.

npm run hot-pick -- feedback --outcome completed --helpfulness improved
# optionally append --file /path/to/local/apply-receipt.json
# Internal checks MUST append --test

Outcomes: completed/failed/abandoned. Helpfulness: improved/same/worse/unknown. A local apply receipt adds only check totals and a stable task ID derived from its plan hash. This is client-reported evidence, not remote attestation. Separate tasks may have identical plans; count this metric as a conservative lower bound.

The dashboard excludes owner jinsim, GitHub Bot accounts, bot handles, test purposes/labels, malformed reports, and duplicate account/task IDs. External reporting accounts are not independently verified people. Bot accounts pretending to be humans and dishonest reports cannot be reliably removed without additional verification. Non-reporting users are unknown. Self-reported usefulness has selection bias and does not establish a causal quality or speed gain; independent paired experiments remain necessary.

Durable dashboard

A dedicated GitHub issue holds the latest health, filtered task outcomes and explicit qualification. One UTC daily comment preserves historical snapshots without paid storage or extra commits. GitHub views/clones are recorded only when API permissions allow them; otherwise they are marked unavailable. These include CI and bots and are never converted into user counts. The repository workflow token usually cannot read traffic; owner-run snapshots can seed traffic evidence without storing a personal token in Actions.

Verification

Unit/integration tests cover stale/failure/recovery, exclusions, duplicate reports, opt-in construction and private-field removal. A real workflow drill validates assigned issue creation; a real owner test report validates exclusion. Test alerts/reports remain clearly marked and closed, never counted as external adoption. Zero external reports means no observed opt-in adoption, not proof of zero users.
